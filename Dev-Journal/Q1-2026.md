# C++ Arc Review

## Reading the core concepts

Reading C++ 17-20, I have seen quite useful things, though it very much is just
the same mess as it is. There's still a lot of redundant functions that are
deprecated. I think that at least I'm in the era where C++ actually improves on
what was since a "do-it-yourself" language, C, not just add on top some features
that may or may not be useful.

If you don't know what I'm talking about, an example of "redundant" functions is
actually ones in C, `snprintf` is a better function than `sprintf`, as this
handles a string buffer, nothing defines "end of string capacity", it needs a
guardrail to be safe, otherwise, nothing will stop it's undefined behavior. Hence
the addition of a `size` parameter.

"Resource Acquisition is Initialization", better known as "RAII", are mindsets
for a developer that uses a "RAII" object, like `std::string`. When I first went
into C++, when I was a Python Baby, I never knew `std::string` could possibly
be freed. This mindset essentially assures the developer, you won't have to
handle this object's memory, I've heard this also avoids `new` and `delete`
code, which is apparently "*bad*".

Lastly, and less noticeably, STL's, this "*T as in Tool*" set is the provider
for some taken for granted objects, like `std::vector`, or for Python `list`,
this dynamically allocates memory for pushing into the list. There's also a
better solution for the classic arrays in C `char* buffer[10];`, which are now
a separate datatype entirely, which is `std::array<char*, 10> buffer;`.

Though I won't be using some of the examples I've mentioned, like `std::array`,
some I will use, since they're literally the key part of some codebases today,
the use-case of `std::vector`, the relief of `std::string` as a replacement for
`char*`'s, etc.

## Project 3: ServRViewR (Rust and C++ observations)

### ServRViewR Prelude

This is for me to observe the differences of Rust, the strengths and
weaknesses of them or whatnot. My main purpose for this project is
to observe the code structure difference, for me to think whichever

This is also a way to get used to the STL of C++, if you haven't
noticed, I haven't mainly touched STL for the past 2 projects. Maybe
the OilCompiler, but that was just an introduction.

### Making the libraries

Making the library structure was simple, I only had to mix the CMake
structure, and implement the structure of ServRLookR. Sorting them, I
could say it was just intuition, though I should mention that I made the
ServRLookR project without any experience of sensible structure itself.

This is more or less the result of me not seeing open source code, which
I should mention is pretty amazing to see, if you're a developer, you
should read some other people's code, it's an amazing presence.

This is the structure of the Project if you want to visualize it:

```none
root/
|- include/
|   | [ Declarations ]
|   |- cmd/
|   |   '-commands.hh      [ Command Struct ]
|   |- data.hh             [  Every Struct  ]
|   |- inputUtil.hh        [ In ServRLookR  ]
|   '- parsers.hh          [  Input Parser  ]
'- src/
    |  [ Definitions ]
    |- cmd/
    |   '- commands.cc
    |- input/
    |   '- inputUtil.cc
    |- parsers/
    |   '- parsers.cc
    '- main.cc             [   Main Logic   ]
```

At the time, I was unknowing of the bad reputation of the use of
"*Utility*" containers/code sections, as they can always be sorted
to better containers to be more verbose of their purpose.

Though, my main mission for this project was to faithfully recreate
the original source. So this was pretty reasonable, I then almost
fell for the trap of making every header library to be public, but
I decided to let the CMake structure take over that one, so I made
it go for a Rust-styled library, where one header includes every
needed private file, so the main code will only include that public
library.

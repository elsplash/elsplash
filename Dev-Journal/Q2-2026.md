### Experimenting with MMap

Going into this, I didn't know much  about `mmap()`, I guessed it was a function that maps
memory into a file. Reading [The Man Pages](https://man7.org/linux/man-pages/man2) we're a
throwback to [cppreference](https://cppreference.com) but *The Man Pages* are more aimed at GNU
tools and the C compiler from what I would guess, moving on, I read that it was for a use-case
to make performance better.

I won't go too in-depth to this, but to put it simply; `mmap()` is used to use a file like memory
to make use of jumping around the file use less computational power. Taking advantage of only
putting modified sections in memory, and mapping the file to memory like scope, etc.

The functions were really robust, and one function I didn't know how to handle errors with,
`open()`, I thought it was the same as every other function made for C, I guessed that it
will return `-1` for the return error, and I was correct! I'm kind of satisfied every time I
guess a rudimentary way to handle it and be correct, it's just my interest for the past.

### What I've learned in MMap

### Making compiling methods with mmap

I learned a bit more about some C error handling. That seems like pretty common sense, I know,
but what I learned was that `perror()` was actually lesser used, and `fprintf(stderr, ...)`
was more preferred.

If you don't know what this means, `perror()` is used for error messages,
if you can't already tell, but it also appends "*: System error*", "*System error*" is a
specialized error message. This, in turn, becomes a problem when you try custom error
messages, as you can't even control the system error message, it doesn't even format too.

`fprintf(stderr, ...)` however, prints out to the same output as `perror()`, even if it
was designed for file output (*I think*). It allows you to optionally add the system error
message within your intended error message with the format feature like `printf()`. The
same result as `perror()` but with more versatility.

## Project 2: Thread Tool

### Experimenting with POSIX Threads

POSIX Threads was pretty easy to understand, though, it's really limiting to pass only 1
argument, though I can think of a obscure way to counter this.I can't really say much
about the way it handles it, I can understand the `...` argument for C being really frowned
upon, but why not?

Anyway, from what I learned, I should initialize a `pthread_t` variable, create a return
variable, then to run a thread, I have to declare `pthread_create(...)` to my return value
variables, and only then `pthread` runs at a given function. Pretty complex if I must guess
from your perspective, but I swear this is really simple to put on code than the entire
routine `mmap()` needs.

It's just 2 initializations and 2 function calls to create and run a thread. I like this
since as I said, I really love simplicity, and this doesn't take more than 1 page to cover
what `pthread_t` does. No seriously,
[Geeks for Geeks](https://www.geeksforgeeks.org/operating-systems/posix-threads-in-os/)
actually explains it all in a short page. One good look in the example code and I got it
instantly.

### Plan for Thread Tool

So, my original plan was to make a CLI like my other project *ServRLookR*, but I guess 2
is already enough, and C was not designed with string parsing in mind, nor even designed
for interfaces either.

My new plan is make it a tool that runs a given argument to execute, like a script or
an executable. This tool will use threads, a hard maximum of double the cores of the
system. The modes will only be 3 for now, which are: `Async` which dynamically picks a
free executable to run, `Queue` which waits for every thread to finish before going
for another burst, and for debugging purposes, `Serial`, which is the same as setting
the `--threads` flag to 1, but picking between the 2 modes gives the same result
regardless.

### Making the libraries

The libraries started relatively small. `rundata.h`, the header for the thread functions,
enums, and structs, only had the `RunMode` enum for the `Async` mode, `Queue` mode, and
`Serial`. I even thought of just putting all the libraries into one header file.

It was relatively simple making the first version of the libraries, though it clearly
needed some refactoring into what it looks like now.

### Making main logic

Making the main logic was easily done than said, just initializing the variables,
calling the functions in order, and handle return errors. Nothing so special, and
nothing special happened in it too.

### Implementing the argument handler library

The library is specialized, so I won't be making a library that gives `parse_arg("-h")`
to be clear. I will make a C version of this, but the plan doesn't include it so this
will suffice for now.

This was a no-brainer, I've made projects that handled arguments before, and I already
knew the structure. `strcmp()` everywhere, I was thinking of making `streq()` since I
was getting annoyed of the repetitive `== 0`'s everywhere, but it wasn't really
necessary.

I've implemented `--threads` for the thread count, which also has warnings to warn you
too many threads can hurt the system. `--help` for the help message. The respective
modes are there, though I haven't accounted for case sensitivity, but I think I'm
better off without needing to account for `qUeuE`. `--force` to bypass the roadblock
for over double the core count thread count. And finally, `--debug` for me.

### Making the thread handling

I may or may not have done this really horribly. At first, I didn't know of any mutex
or any thread locks, since I haven't read any documentation about `pthread.h`, though
for me, I thought I knew everything about `pthread.h` after experimenting with it.

I tried to synchronize via states, which was done horribly. Looking at it now, using
`pthread_mutex_t` was obvious. As this protects the thread that "*locks*" the process,
so everything will wait for the mutex to "*unlock*". The state in question was my try
of everything waiting, which, if you can't already tell, used `while (true) for (...)`
which is a CPU burner.

After implementing `pthread_mutex_t` and realizing the function parameter for
`pthread_create()` only accepted one argument, I also implemented a `ThreadConfig`.
This, in turn, will make me do a mistake really quiet, and stealthy, it's stupid.

### Debugging

Now, the debugging process was similar to the other debug sessions, many bugs to fix,
and overlooked methods that the compiler errors in. Though the bug I encountered was
something I wasn't really expecting.

This bug was really unclear, it just halted my program, looking at the debug, which was
unpolished by the time I encountered it, this bug also made me polish the debug prints.
What also stumped me was this was also happening in the debug run mode `Serial`.

I added some extra debug prints in the `fetch_index()` function all the threads were
using, since all the threads we're stopping there, it stopped at locking the mutex.
This was confusing since I was certain I initialized the ThreadConfig's mutex correctly,
I even replaced the separate `pthread_mutex_init()` function to adding `PTHREAD_MUTEX_INIT`
to the lock instead, and still didn't work.

After looking endlessly at the confusing debug prints and "*no error*" code. I just
thought "*Is `pthread_create()` the problem?*" I checked it's function signature using
VS Code's hover details, and what I realized was, kind of embarrassing.

### My epiphany

I realized, `pthread_create()` runs the thread, and not `pthread_join()` nor
`pthread_detach()`, they only declare what the program is gonna do to them for the OS's
sake. What's even more embarrassing, is that I realized the `ThreadConfig*` variable cast
stacking I was doing, completely redundant, I passed an address of a `void*` pointer to
the config's address.

Now, embarrassed to even describe how silly of a mistake I made, I mean who would have
guessed? I didn't read any documentation for anything. I did one more scan and fixed the
issues I overlooked, even the loops that we're supposed to be `i < threadCount`, was
wrongly declared `i < pathCount`, I didn't even notice this with the debug flag on.
